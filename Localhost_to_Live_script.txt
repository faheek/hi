Backend and database hosting.
Moving our A S P dot NET and SQL setup over to Azure.
Now, getting the heavy lifting of the backend and database onto the Internet does require some meticulous configuration.
The creator utilized an Azure app service to host the web API and an Azure SQL database to hold the actual data.
If you haven't used it, an Azure app service is essentially a platform as a service.
It completely removes the massive burden of provisioning bare metal servers or manually managing complex configurations.
You literally just log into Azure, create a new web app, pick a server region, and hand Azure your code.
It handles all the underlying infrastructure for you.
And once deployed, checking the overview monitor to verify that the status officially says "running" is just the ultimate sanity check before wiring the rest of your architecture together.
When you're shifting from a local database instance to a live Azure SQL database, updating your connection string in the JSON file is the absolute lifeline connecting your cloud API to your cloud database.
Without it, your live API just cannot fetch or store any of your application's data.
However, and this is a huge however, a core tenet of modern deployment is security.
You must never ever hardcode this live Azure SQL connection string directly into your source code, or accidentally commit it to a public GitHub repository.
Doing so is basically an open invitation for malicious actors.
Instead, we use secure, injected environment variables directly within the Azure portal to safely override this configuration in production.
Okay, section five, troubleshooting production issues, or as I like to call it, facing the trials of deployment.
Because let's be real, pressing a deploy button is simple, but configuring separate architectures to speak securely across the open internet takes serious work.
Errors aren't just common, they are an expected part of the process.
Take cross-origin resource sharing, or CORS.
It is the ultimate rite of passage, and frankly, the bane of every full stack developer's existence.
When your app lived entirely on your local machine, the browser implicitly trusted the communication between the front and back end.
But in production, you've got a Vercel domain trying to speak to an entirely different Azure domain.
The browser immediately blocks this as a massive security risk, unless the backend explicitly provides headers permitting that specific origin.
Untangling these HTTP configurations and correctly issuing keys for secure online authentication, these struggles are the true learning curve of taking an application live.
