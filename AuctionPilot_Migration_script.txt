All right, section four, managing simultaneous bidding conflicts, the concurrency problem.
Let's look at a really practical micro-narrative here.
What happens when two users try to place a bid at the exact same millisecond?
Imagine the current price of an item is a thousand pounds.
Buyer A and Buyer B are staring at the exact same screen, both reading version 1 of the auction at precisely the same time.
Buyer A quickly hits submit, saves a bid and pushes the auction safely up to version 2.
Now, if Buyer B clicks Submit just a fraction of a second later, trying to save a bid based on that old one thousand pound price, they're blocked.
Our concurrency protections kick in.
They are forced to refresh the page, see the new price, and validate it before trying again.
This race condition is honestly one of the trickiest parts of e-commerce to get right.
So how do we solve this?
The application utilizes a clever system column in PostgreSQL called the xmin value.
If you want a really easy way to picture xmin, compare it to pulling a ticket at a deli counter.
When you look at the auction, you're handed a ticket number.
When you finally go to make your bid, the database checks if the current ticket number actually matches the one you were holding when you made your decision.
If those numbers don't match, it means the auction changed while you were deciding.
You have to get back in line, look at the new price and get a new ticket.
This safely handles conflicts and just rolls back transactions rather than silently blindly accepting a stale update.
Docker images and timeouts, packaging and background tasks.
Next, we have to tackle how the application is packaged in Docker and why that creates a really unique headache for storing images.
There's a golden rule for containerized apps.
Files stored inside the backend container should never, ever be treated as permanent storage.
Why?
Because of a concept we can call container amnesia.
Docker containers are inherently ephemeral.
They can be destroyed, scaled up, or restarted dynamically at any second by the hosting provider.
If you save a user's auction avatar directly onto the local disk of a Render container, poof!
It's going to completely vanish the next time the app goes to sleep and restarts.
We absolutely needed a dedicated external storage solution.
So we solve this container amnesia with a very precise three-step flow to push files out to Cloudinary.
First, the user sends the file to the backend, which does all the security validation.
Then the backend securely uploads the file to Cloudinary.
Finally, the application stores the reference and returns the public image URL.
Now, we use this three-step dance for one absolutely critical reason, security.
If the front end uploaded directly, we'd have to expose our top secret Cloudinary API keys to the public web in the React code.
By routing it through Render instead, those secrets stay tightly locked in the backend vault.
Now, moving to free-tier cloud hosting introduces some fascinating edge cases.

To combat this, our strict logic ensures we validate bids against the actual server time, aggressively rejecting late arrivals.
We also run recovery processing to safely close out those expired auctions.
